# Project scope

Agreed by Group 2 on 2026-11-17. Change this file through a PR, and add or supersede an ADR in [`docs/adr/`](adr/) when a decision changes.

## Goal

Build a fully automated, reproducible MLOps pipeline that ingests a real insurance dataset, trains and registers a claim-frequency model, serves it as a containerized API, and monitors it for drift. The course grades engineering rigor, reproducibility, and system design rather than model accuracy, so effort goes into the pipeline, not into squeezing out the last point of deviance.

- **Final presentation:** Monday 2026-12-07 (Week 10), 10 minutes plus Q&A. Slides are submitted the same day.
- **Runs entirely on a local machine** with `docker compose`. No cloud deployment ([ADR-0008](adr/0008-local-docker-compose-only.md)).

## Problem

Predict the **claim frequency** of each policy, the expected number of claims per policy-year (`ClaimNb / Exposure`), from driver, vehicle, and region attributes. An insurer uses it to price premiums and to detect shifts in portfolio risk.

## Data

- **Source:** OpenML dataset 41214 (`freMTPL2freq`), CC0, 678,013 policies, 12 columns ([ADR-0001](adr/0001-openml-as-data-source.md)).
- **Ingestion quirks:** `IDpol` arrives as float (cast to int), `VehGas` values keep literal single quotes (strip them), and columns must be aligned by name, never by position. `Region` stays as INSEE codes (`R11`–`R94`).
- **Split:**
  - Test: a random 20% with a fixed seed, versioned with DVC. It is not touched during model selection. It is used only for the final evaluation of the champion and for the baseline validation through the API (syllabus 4b).
  - The remaining 80% becomes train (70% of the full data) and validation (10% of the full data).
- **Known limitation:** this is the pre-2022 CASdatasets version. The 2022 revision drops 22 policies and lowers `ClaimNb` on 9,095 rows (total claims go from 36,102 to 26,444). Stretch goal 1 adopts the revision as data v2.

## Metrics

See [ADR-0002](adr/0002-poisson-deviance-selection-metric.md). Every training run computes and logs all three metrics with the same evaluation code that monitoring uses.

| Metric | Role | Business question | What failure looks like |
|---|---|---|---|
| Exposure-weighted mean Poisson deviance | **Selects models** (config `selection_metric`, evaluated on validation only) | Does the model fit claim counts well? | — |
| Gini (Lorenz curve) | Reported | Does it rank risky policies above safe ones? | Adverse selection: a competitor that ranks better undercuts us on good risks, and we keep the bad ones |
| Calibration ratio (predicted claims / actual claims) | Reported, also used in production monitoring | Does total premium cover total claims? | A ratio below 1 means we under-price the portfolio and lose money |

The **baseline model** is a constant model that predicts the portfolio's mean frequency. Every candidate must beat it.

## Pipeline

The stages map to the syllabus Technical Project Outline.

| Syllabus stage | What we build |
|---|---|
| 1. Data ingestion and baselines | DVC stages `ingest → clean → split → drift sets`, with DagsHub as the shared remote ([ADR-0004](adr/0004-dvc-with-dagshub-remote.md)); the constant baseline |
| 2a. Orchestration | Airflow 3 with `LocalExecutor`. Each task runs the `trainer` image via DockerOperator ([ADR-0003](adr/0003-airflow-with-docker-operator.md)). DAGs: `training` (`dvc repro` → train → evaluate → register) and `monitor` |
| 2b. Experiment tracking | MLflow. Candidates: constant baseline, Poisson GLM, LightGBM (Poisson), and FLAML AutoML over LightGBM / XGBoost / HistGB with a forced Poisson objective ([ADR-0006](adr/0006-flaml-for-automl.md)). Each AutoML trial is a nested run. Every run records the git commit and the DVC data hash (lineage) |
| 2c. Model registry | Semantic version tag on every model version; `challenger` and `champion` aliases; promotion is a human `promote` command ([ADR-0007](adr/0007-semver-and-human-promotion.md)) |
| 3. Containerization and deployment | FastAPI `api` image that loads `models:/claim-frequency@champion` at startup |
| 4. Monitoring | Prediction log in Postgres, delayed ground truth, an Evidently `monitor` DAG, the Evidently UI dashboard, and alerts |
| 5. Drift simulation | Five scenarios generated by one script and versioned with DVC |

### Responsibilities of the tools

- **DVC owns data:** what each data version is and how it was produced (`dvc.yaml`, `dvc.lock`).
- **MLflow owns models:** experiments, metrics, artifacts, and the registry.
- **Airflow owns when and in what order** steps run.

Automation never commits to git. When a data version changes, the new `dvc.lock` lands through a normal PR together with the code change that caused it. A routine DAG run on unchanged data leaves `dvc.lock` untouched.

## Services

There is one `docker compose` stack:

| Service | Purpose |
|---|---|
| `postgres` | One server with three databases: `airflow`, `mlflow`, `monitoring` |
| `mlflow` | Tracking server and model registry, with artifacts served by the server |
| `airflow-*` | API server, scheduler, and DAG processor (`LocalExecutor`; no Redis or Celery) |
| `trainer` | Image with the ML package and CLI. DockerOperator launches it; developers can run it directly with `docker compose run trainer ...` |
| `api` | FastAPI prediction service |
| `evidently-ui` | Monitoring dashboard |

## Serving

- `POST /predict` takes one or more policies with raw rating factors and returns the predicted annual frequency per policy plus the model's semantic version.
- Pydantic validates types and plausible ranges (for example `DrivAge` 18–100). Invalid requests get HTTP 422.
- `GET /health` reports liveness for Docker health checks. `GET /model-info` reports the served version, its training date, and its metrics.
- Every request and prediction is written to `prediction_log` in Postgres.
- Switching models means moving the `champion` alias and restarting the `api` container. It needs no code change and no image rebuild.

## Monitoring and alerts

- **Reference dataset:** the validation split together with the champion's predictions on it.
- **Checks:** data drift and prediction drift on logged traffic. Once ground truth arrives, also Poisson deviance and the calibration ratio on live traffic.
- **Delayed ground truth:** claim outcomes are known only after the policy period, so a simulated claims feed writes actual `ClaimNb` to a `ground_truth` table after the predictions.
- **Dashboard:** the `monitor` DAG pushes Evidently snapshots to the Evidently UI as a time series.
- **Alerts:** a failed Evidently test fails the Airflow task, which turns red in the Airflow UI. If `ALERT_WEBHOOK_URL` is set in `.env` (a Discord webhook on the demo machine), a message is also posted there. Without it, alerts go to the log only.
- **No false alarms:** sending the clean test set through the API must not trigger an alert.

## Drift scenarios

`simulate_drift.py --scenario <name>` corrupts the test set. Each output is versioned with DVC.

| Scenario | Corruption | Expected detection |
|---|---|---|
| `schema_break` | Rename a column or send a wrong type | API returns 422; monitoring shows a spike in the rejection rate |
| `out_of_bounds` | Impossible values (e.g. `DrivAge = 250`, negative `BonusMalus`) | API validation rejects the requests |
| `column_swap` | Swap `VehAge` and `VehPower`. Values stay plausible, so validation passes | Only Evidently's distribution checks catch it: a silent failure |
| `portfolio_shift` | Resample toward young, urban drivers (lower `DrivAge`, higher `Density`) | Data drift, and the mean predicted frequency rises |
| `concept_drift` | Same feature distribution, higher true claim rate | Data drift tests pass; the calibration ratio fails. Shows why data drift alone is not enough |

The story is a two-layer defense. API validation blocks impossible inputs; Evidently catches inputs that look plausible but whose distribution has shifted.

## Engineering practices

- `uv` with `pyproject.toml` and `uv.lock`, pinned to Python 3.12 (`uv python pin 3.12`, uv-managed interpreter). `requirements.txt` is exported for graders.
- **GitHub Actions on every PR:** ruff (lint and format), pytest (unit tests on fake data, with no Airflow or MLflow needed), and a build of the `trainer` and `api` images. CI must pass to merge.
- `main` is protected once CI exists: no direct pushes, and every change goes through a PR.
- Every task is a GitHub Issue; PRs link it with `Closes #N`.
- **Contracts first.** Before parallel work starts, one PR defines the shared contracts, each with fakes or stubs, so that roles do not wait on each other:
  1. Data schema: column names, types, valid ranges.
  2. Model contract: registered model name, aliases, input and output format.
  3. Log schema: the `prediction_log` and `ground_truth` tables.
  4. CLI contract: the `trainer` commands and the paths each one reads and writes.

## Stretch goals

In priority order. Each stretch goal is owned by the role that owns the adjacent core work, so they can run in parallel.

1. **Data v2 (Role A):** adopt the 2022 CASdatasets revision as a new DVC data version, retrain, and bump the model version by MINOR.
2. **Automatic retraining trigger (Role C):** the `monitor` DAG triggers the `training` DAG when drift is detected.
3. **Health monitoring (Role D):** Prometheus and Grafana for API latency and error rate.
4. **Feature store:** only if everything else is done.
